# HiveBooks: власні зміни та оновлення з upstream

Ваші зміни коду живуть у вашому git-репозиторії. Коли автор публікує оновлення (наприклад, нову форму звіту),
ви підтягуєте його однією командою `./update.sh`, а ваші зміни зберігаються.

## 1. Свій репозиторій

Потрібні git, Docker і Docker Compose v2.

**Варіант А: fork на GitHub** (для публічного репозиторію). Натисніть **Fork** на GitHub, потім:

```bash
git clone https://github.com/ВАШ_АКАУНТ/HiveBooks.git
cd HiveBooks
git remote add upstream https://github.com/OlexandrDevelop/HiveBooks.git
```

**Варіант Б: власний (в тому числі приватний) репозиторій**. Створіть порожній репозиторій на GitHub, потім:

```bash
git clone https://github.com/OlexandrDevelop/HiveBooks.git HiveBooks
cd HiveBooks
git remote rename origin upstream
git remote add origin https://github.com/ВАШ_АКАУНТ/ВАШ_РЕПОЗИТОРІЙ.git
git push -u origin main
```

Результат: `origin` — ваш репозиторій (куди ви надсилаєте зміни), `upstream` — репозиторій автора (звідки беруться оновлення).
Перевірка: `git remote -v`. Для приватного репозиторію автора потрібен доступ на читання.

## 2. Режим розробки

```bash
./install.sh --dev
```

Каталог із кодом підключається до контейнерів, увімкнено `developer_mode`. Сайт доступний лише на цьому комп'ютері
(`http://localhost:8080`). **Не відкривайте режим розробки в мережу й не використовуйте його на сервері.**

- Зміни Python у вашій IDE діють з наступного запиту (backend перезавантажується сам, це займає кілька секунд). Для фонових задач:
  `docker compose restart worker scheduler`.
- Зміни JS/CSS діють після жорсткого оновлення сторінки (Ctrl+Shift+R). Перебудова образу не потрібна.
- Зміна JSON DocType у IDE: `./bench.sh migrate`.
- DocType, звіт чи друковану форму, змінені в інтерфейсі, записано у файли вашого каталогу, тож вони потрапляють у git.
- На Linux, якщо ваш uid не 1000, скрипт покаже команду `setfacl`, щоб контейнер міг писати у файли.

Повернення до звичайного режиму: `./install.sh --prod` (один раз перебудовує образ; спершу зробіть commit).
Дані в обох режимах ті самі.

## 3. Власний застосунок `owner_custom` (рекомендовано)

Файли upstream (`ua_accounting/`) оновлюються автором, тому правки в них можуть давати конфлікти. Для ваших змін створіть
власний застосунок. Каталог `owner_app/` автор ніколи не змінює, тому конфліктів там не буває.

```bash
./new-owner-app.sh      # створює owner_app/ один раз
./install.sh            # встановлює застосунок на сайт (у режимі розробки додайте --dev)
git add owner_app && git commit -m "Власний застосунок"
```

Застосунок підхоплюють `install.sh` і `update.sh` автоматично (також на Easypanel).

### Що можна зробити в `owner_custom` без правки upstream

| Потреба | Як |
|---|---|
| Нове поле або зміна властивостей чужого DocType | Налаштувати форму (Customize Form) → **Export Customizations**, модуль **Owner Custom**; файл потрапить у `owner_app/` |
| Новий DocType, звіт, друкована форма | Створіть в інтерфейсі в режимі розробки з модулем **Owner Custom**: файли з'являться в `owner_app/owner_custom/owner_custom/` |
| Серверна логіка при збереженні/проведенні | `doc_events` у `owner_app/owner_custom/hooks.py` |
| Підміна методу контролера | `override_doctype_class` (один застосунок на DocType) |
| Свій API-метод | функція з `@frappe.whitelist()` у `owner_app/owner_custom/api.py` |
| Скрипт для чужої форми/списку | `doctype_js`, `doctype_list_js` |
| Власні поля як fixtures | `fixtures` у hooks і `./bench.sh export-fixtures --app owner_custom` |
| Планові задачі | `scheduler_events` |

Приклад: серверний метод. Створіть `owner_app/owner_custom/api.py`:

```python
import frappe

@frappe.whitelist()
def hello():
    return "привіт"
```

Виклик: `http://localhost:8080/api/method/owner_custom.api.hello`. У режимі розробки метод працює одразу після збереження файлу.

### Що потребує прямої правки upstream

- зміна внутрішньої функції, яка не є hook або whitelisted-методом (правила проведення, рушій звітів);
- видалення чи перебудова полів стандартного DocType (приховати поле можна через Property Setter);
- зміна готового звіту чи друкованої форми «на місці» (краще скопіювати у свій застосунок);
- виправлення помилки автора.

Прямі правки дозволені: редагуйте файли в `ua_accounting/` і робіть commit. Це найчастіша причина конфліктів під час оновлення.
Не зберігайте в інтерфейсі чужі DocType у режимі розробки без потреби: `developer_mode` перепише їхні JSON-файли.

## 4. Збереження змін у git

```bash
git status
git add -A
git commit -m "Опис змін"
git push origin main
```

## 5. Оновлення з upstream

```bash
./update.sh
```

Скрипт: перевіряє, що немає незафіксованих змін; додає `upstream`, якщо його немає; отримує зміни; робить резервну копію сайту;
зливає `upstream/main` у вашу гілку; перебудовує образ і виконує міграції. Ваші commit і дані зберігаються. Нічого не
надсилається на GitHub: після успіху виконайте `git push origin main`.

Якщо скрипт каже про незафіксовані зміни, зробіть commit (розділ 4) або `git stash`.

## 6. Конфлікт під час оновлення

Конфлікт буває, коли ви і автор змінили ті самі рядки одного файлу. `./update.sh` тоді:

1. показує список файлів із конфліктом;
2. **скасовує злиття** (`git merge --abort`): ваші файли такі, як були, сайт працює, дані не змінено;
3. завершується з кодом 2 і підказкою.

Що робити:

```bash
git merge upstream/main          # злиття знову, з позначками конфлікту у файлах
# відкрийте файли зі списку в IDE; у блоках <<<<<<< ======= >>>>>>> залиште потрібний код
git add ШЛЯХ/ДО/ФАЙЛУ
git commit
./update.sh                      # завершить оновлення: перебудова і міграції
```

Поки в файлах є позначки `<<<<<<<`, у режимі розробки сайт може показувати помилки: завершіть злиття або скасуйте його
командою `git merge --abort`. Щоб уникнути конфліктів, тримайте зміни в `owner_app/`.

Якщо оновлення зламало сайт після злиття (код виходу 3): `git reset --hard ХЕШ_З_ПОВІДОМЛЕННЯ && ./install.sh`.
Резервна копія лежить у томі `sites`, каталог `sites/ВАШ_САЙТ/private/backups` контейнера backend.

## 7. Easypanel

Easypanel збирає Dockerfile з репозиторію, який ви вказали. Використовуйте **свій** репозиторій (fork), а не upstream:

1. Створіть Compose service з джерелом — ваш репозиторій, Build Path `/` (див. `DEPLOY.md`).
2. Оновлення: на своєму комп'ютері `./update.sh` (без локального встановлення він лише зливає код), далі `git push origin main` і **Deploy** в Easypanel.
   Збірка образу запускає міграції. Для fork без конфліктів можна натиснути **Sync fork** на GitHub, а потім Deploy.
3. Режим розробки на Easypanel не підтримується: тільки локально.
